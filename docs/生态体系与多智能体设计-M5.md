## 0. 先说清楚科学边界（必读）

后面的设计有一个必须先讲明白的前提，否则会误导人：

**FlyWire 连接组是"一只成年雌性果蝇"的脑，不是通用大脑。** 把它挂到青蛙身上、或让多只果蝇"共享"它，
在神经科学上是**隐喻，不是仿真**。本项目做这件事的理由是**游戏性与观感**，不是科学结论：

- 「多果蝇共用连接组」的诚实表述是：*同一个神经系统，被放在不同的处境里*。
  个体差异来自处境（刺激、内驱力、位置）而非脑结构 —— 这本身是个有意思的哲学点，但它不是生物学事实。
- 「青蛙用果蝇脑」的诚实表述是：*把同一套连接组驱动电路换个身体和几个驱动量*。
  真实的蛙脑与蝇脑在结构与规模上完全不同，绝不能说"青蛙的脑就是果蝇的脑"。

因此 App 内所有相关文案必须**明确标注为科普隐喻**，「关于」页补一段说明。
若不做这个标注，本项目就从"科普演示"变成了"伪科学演示"——不能接受。

## 1. 目标与原则

### 1.1 目标

1. **多智能体**：同一场景内 N 只果蝇（默认 3 只，可配 1~6），彼此可感知、可竞争、可合作，
   出现**用户没写死的**群体行为（争食、避让、跟随、结群）；
2. **统一大脑**：所有生物（多只果蝇 + 青蛙）共用**同一套连接组仿真**，
   而不是各自跑一份 —— 既是为了性能，也是为了"同一套神经系统"这个概念表达；
3. **生态闭环**：食物 → 果蝇 → 青蛙，能量单向流动；
   青蛙**只能靠捕食果蝇存活**（不吃就饿死/离场），果蝇靠用户投喂与树上果实存活。
   用户从"喂一只虫"变成"维持一个小生态"；
4. **场景切换**：支持在多个场景/预设间切换（生态沙盒 / 单只观察 / 大脑点云 / 昼夜长镜头等），
   切换尽量瞬时、不重新加载 3D 引擎。

### 1.2 设计原则

- **行为层保持纯逻辑且可实例化**：现有 `FlyBrain` 已经是不依赖渲染的纯逻辑类，
  多实例只需 `new FlyBrain(cfg)` —— 这一层改动最小（主要解决"配置是否共享"与"个体参数微差"）；
- **渲染层按个体隔离节点集合**：每只果蝇一组 `fly_i / wing_left_i / wing_right_i / head_pivot_i`，
  由 `FlyRenderer` 按实例持有各自的节点引用（把现在的"单例字段"改成"每实例一组引用"）；
- **大脑是共享资源，不是每体的资源**：连接组仿真只跑一份（现有 `BrainWorker`），
  多智能体通过**读写不同的神经元群**接入（见 §2）；
- **性能红线**：3 只果蝇 + 1 只青蛙时，连接组 tick 不得超过现有单体的 1.2 倍（当前 ~65ms / 100ms 预算）；
  纯逻辑（寻路/碰撞/通信场）合计每帧 < 2ms；
- **一切可关**：多智能体、青蛙、连接组驱动三个维度各自可开关，低端机可退化为 M4 形态。

## 2. 统一大脑架构：BrainMount（核心抽象）

### 2.1 现状与问题

现在 `ConnectomeDriver` 是"果蝇专用"的：它把 App 事件映射到固定的神经元群
（食物气味→OLF_ORN_FOOD、触碰→MECH_BRISTLE…），再把运动群放电汇总成行为累积量。
要支持"多只果蝇各自接入"和"青蛙也接入"，需要把这层映射**抽成可参数化的配置**。

### 2.2 BrainMount 设计

```
              ┌──────────────────────────────┐
              │  BrainWorker（单例，139,255） │   ← 只跑一份
              │  LIF 仿真 10Hz + 群门控       │
              └──────────────┬───────────────┘
                             │ 群放电统计（每 tick）
        ┌────────────────────┼────────────────────┐
        ▼                    ▼                    ▼
  BrainMount#0         BrainMount#1         BrainMount#2   ← 每只生物一份"接线图"
  （果蝇 A）            （果蝇 B）            （青蛙）
  感觉群映射表          感觉群映射表          感觉群映射表
  运动群读取表          运动群读取表          运动群读取表
  内驱力↔群刺激         内驱力↔群刺激         饥饿↔群刺激
```

**`BrainMount`（接线座）= 一份声明式的群映射配置 + 每帧的读写：**

| 组成 | 说明 |
|---|---|
| `senses: SenseMap[]` | 该生物的"感官"→ 神经元群。例如果蝇：食物气味→`G_OLF_FOOD`；青蛙：视觉运动→`G_VIS_LO` |
| `actuators: ActuatorMap[]` | 神经元群 → 该生物的"动作通道"。例如果蝇：`G_VNC_CPG`→步速；青蛙：`G_MN_PROBOSCIS`→舌头弹出 |
| `drives: DriveMap[]` | 该生物的内驱力 ↔ 驱动群。例如果蝇：饥饿↔`G_DRIVE_HUNGER`；青蛙：饱食度↔`G_DRIVE_HUNGER`（语义借用） |
| `groupOffset: number` | **个体偏移**：给不同果蝇分配群号偏移量，使它们的"接入点"不完全重合（见 2.4） |

**为什么用"同一份仿真 + 不同接线"，而不是每只跑一份？**
- 性能：一份 139k 神经元已经是 65ms/tick，N 份直接不可行；
- 概念：这正是"同一套神经系统、不同处境"的表达；
- 实现：`ConnectomeDriver` 里已按群汇总放电（`GROUP_SIZES` / 群编号常量），
  把"固定群号"换成"配置里的群号"即可，增量可控。

### 2.3 青蛙的 BrainMount（同一套脑、不同身体）

| 环节 | 果蝇 | 青蛙 |
|---|---|---|
| 视觉输入 | 光照档位 → `VIS_R1R6` | 视野内果蝇距离/运动 → `VIS_LO` + `VIS_LPTC`（捕食者靠运动检测，符合真实蛙类） |
| 嗅觉 | 食物气味 → `OLF_FOOD` | 果蝇气味 → `OLF_FOOD`（同一群，语义借位） |
| 运动输出 | `VNC_CPG` → 步速 | `VNC_CPG` → 转向/跳跃助跑 |
| 攻击输出 | `MN_PROBOSCIS` → 觅食意图 | `MN_PROBOSCIS` → **舌头弹出** |
| 恐惧 | `MECH_BRISTLE` → 惊吓 | 无（青蛙不被捕食，不设恐惧） |
| 内驱力 | 饥饿/疲劳/好奇/恐惧 | **饱食度**（唯一驱动：必须吃果蝇） |

**接线差异就是"身体差异"**：同一份放电，接到不同的执行器上，就产生不同的行为。
这是本设计里最有价值的一点 —— 它让"同一套脑"这句话在代码层面也成立，而不只是文案。

### 2.4 个体差异怎么来（避免 N 只果蝇完全同步）

若 N 只果蝇的接线完全相同，它们会像同一个模子刻出来的木偶，行为高度同步、看起来很假。
三个来源引入差异（按代价从低到高）：

1. **处境差异（零成本，必做）**：位置、朝向、看到的食物、是否被碰到各不相同 ——
   连接组是混沌系统，初始条件微小差异会放大成不同轨迹；
2. **参数微差（低成本，推荐）**：每只果蝇的 `FlyConfig` 做 ±10% 的个体扰动
   （走路速度、朝向偏好、疲劳阈值、进食速度），并给一个 `personalitySeed`；
3. **群偏移（中成本，可选）**：给第 i 只果蝇 `groupOffset`，使它的刺激注入落在
   相邻的神经元群上（如视觉 `R1R6` 与 `R7R8`）。这在神经学上对应"个体间感受器分布差异"，
   但要小心别把群语义映射错 —— 必须由 `neuron_meta.json` 的真实群表驱动，不能手工编。

> **决策建议**：首版只做 1 + 2，第 3 项列为可选实验。理由是 1、2 已足够产生差异，
> 而第 3 项一旦映射错群，行为会变得无法解释。

## 3. 单场景多果蝇

### 3.1 场景侧改造

| 项 | 方案 |
|---|---|
| 节点 | `world.glb` 烘焙 N 组果蝇树：`fly_0…fly_{N-1}`，各自带 `wing_left_i / wing_right_i / head_pivot_i`。N 上限 6（再多没必要，且面数吃紧） |
| 渲染器 | `FlyRenderer` 从"持有单组节点"改为 `FlyRenderer.attach(nodeSet)`，页面持有数组 `renderers[i]` |
| 行为 | `brains[i] = new FlyBrain(cfg_i)`，`cfg_i` 为个体扰动后的配置副本 |
| 统计 UI | 状态行改为"群体摘要"（例：`3 只 · 饿均 62% · ❤ 平均 78`），点开可看个体列表 |

### 3.2 个体间互动的物理与信息层

| 机制 | 实现 | 产生的观感 |
|---|---|---|
| **避让**（有实体感） | 个体间距 < 0.25 时互相施加斥力（纯逻辑，O(N²)，N≤6 无所谓） | 不会互相穿模 |
| **争食** | 食物是**共享的有限资源**（保持现有 5 份上限）；`nearestFood` 返回被抢的那份时，落后者得到"已被占"标记后重新选目标 | 抢食、"先到先得" |
| **食物耗尽压力** | 投喂总量有限 → 饥饿竞争。这是"竞争"最直接、最好懂的来源 | 围绕食物聚集 |
| **保食**（可选） | 正在进食的果蝇对靠近者施加威慑（`fear` 小幅上升） | 护食 |
| **惊吓传染**（合作雏形） | 一只被青蛙攻击/被触碰 → 以其为圆心半径 1.5 内的同伴 `fear += 0.3` | "一只有事全都跑" |
| **信息素场**（合作核心） | 一张低分辨率 2D 标量场（如 24×24 覆盖活动区），两种成分：**食物味**（吃到食物的位置沉积、随时间衰减）与**警报味**（被攻击位置沉积）。果蝇感知所在格浓度，作为 Wander 的转向偏置 | **stigmergy（痕迹通信）→ 自发聚集与集体避让**，这是最可能出现"涌现"的地方 |

> **为什么把信息素场作为合作的主机制**：真实蚁群/蝇群的关键协作不是"互相商量"，
> 而是"改变环境、别人读环境"。这个机制实现便宜（一张二维数组 + 每帧扩散衰减），
> 却能产生可观察的集体行为（路径被强化、危险区被集体回避）。
> 而且它**不需要个体间直接通信**，与"纯逻辑行为层"的架构完全兼容。

### 3.3 群体行为验收（怎么判断真的"涌现"了）

不写死任何群体动画的前提下，以下现象应当**自发出现**（不是脚本）：

1. 两只以上果蝇在同一份食物附近先后到达 → 出现"抢食"（后者被威慑或改道）；
2. 其一受惊 → 附近同伴同帧逃离（惊吓传染）；
3. 投喂点固定后，多次投喂会出现"路径强化"：果蝇更倾向于沿已有食物的方向搜索；
4. 青蛙多次在同一区域得手 → 该区域被集体回避（警报味沉积）。

若 1~4 都观察不到，说明机制没生效，不要用"涌现需要更长时间"来搪塞 —— 那是设计失败。

## 4. 青蛙：同一套大脑，只能靠捕食果蝇生存

### 4.1 生存闭环

```
饱食度 satiation：0~1，初始 0.6
  - 自然衰减：-1/180 秒（即 3 分钟不吃就会饿到 0）
  - 成功捕食一只果蝇：+0.45（约两只能吃饱一段时间）
  - satiation = 0：青蛙进入虚弱（移动变慢、不再攻击）→ 持续 20s → 离场（隐藏）
  - 离场后 30s 在岸边重新出现、satiation = 0.5（生态自我恢复，避免用户看着空场景）
```

**这条闭环是整个生态设计的骨架**：
- 果蝇不吃东西会饿死（M4 已有 HP 机制）；
- 青蛙不吃果蝇会饿到离场；
- 所以"用户不投喂 → 果蝇少 → 青蛙也活不成"，用户的一次投喂会沿食物链放大。

### 4.2 捕食流程（在 M4 基础上扩展）

| 阶段 | 变化 |
|---|---|
| 索敌 | 警戒圈改为**动态**：`satiation` 越低，警戒圈越大（饿急了更主动）；饥饿时 `2.2 → 3.2` |
| 蓄力 | 保留 0.8s 救援窗口（M4 已有），但**每次成功捕食后饱食度上升 → 攻击欲下降**，避免连续屠杀 |
| 攻击 | 命中后除扣血外，新增：**该果蝇被"叼走"**（拖向青蛙 0.4s，位置由青蛙驱动）→ 若 HP 归零则在青蛙嘴边消失（而非原地翻面），青蛙饱食度 +0.45 |
| 饱和 | `satiation > 0.8` 时不再主动攻击，只做待机鼓腮 —— 给用户喘息，也让"喂饱青蛙"成为一种玩法（牺牲一只换取全场安全） |

> **一个有意思的副作用**：用户可以主动"投喂青蛙"（把它喂饱换和平），
> 也可以"吹风救援"（M4 已有）。两条策略的取舍就是玩法深度。

### 4.3 青蛙也吃果蝇的"尸体"？（明确不做）

不做。理由：会让果蝇死亡失去代价，且"清道夫"角色更适合留给 M5 之后的蚂蚁（§8 可选池）。

## 5. 能量流与生态参数表

| 环节 | 参数 | 默认值 | 说明 |
|---|---|---|---|
| 食物来源 | 用户投喂 | 无限（每次 1 份，场上上限 5） | 用户是"生态外部的能量输入" |
| 食物来源 | 树上果实 | 3 棵 × 3 颗 = 9 颗，每颗一次性 | 自然衰减的资源，被吃完就没了；60s 后重新结出 |
| 果蝇消耗 | 饥饿 0.008/s + 移动加速饥饿 | 现有 M4 参数 | 一只果蝇约 4 分钟吃一份 |
| 果蝇死亡 | HP ≤ 0（饿死/被捕食/落水） | 现有 | 死亡 5s 后原点重生 |
| 青蛙消耗 | 饱食度 -1/180s | 新增 | 3 分钟不吃就虚弱 |
| 青蛙收益 | 每只果蝇 +0.45 | 新增 | 约 6~7 分钟捕食 1 次才能维持 |

**自持性检验（纸面推演）**：3 只果蝇 + 9 颗果实 = 约 36 分钟的食物 → 3 只果蝇各自 4 分钟一份
≈ 27 分钟内吃光 → 所以**果蝇必须有无限的食物来源（用户投喂）**，否则生态在半小时内崩溃。
这条推演说明：**用户的投喂不是"玩法之一"，而是这个生态的能量输入口**，必须在引导文案里讲清楚。

## 6. 性能与降级

| 维度 | 3 只果蝇 + 青蛙 | 降级策略 |
|---|---|---|
| 连接组 tick | 目标 ≤ 78ms（现 ~65ms） | 每体接线只读**汇总后的群统计**（O(群数)），不新增逐神经元开销 |
| 纯逻辑 | 群体互斥 + 信息素场 + 互动判定 | 信息素场固定 24×24，每帧 576 格；扩散用两次简单卷积，可降到每 3 帧一次 |
| 3D 节点 | 189 + N×~35 ≈ 300 | 果蝇刚毛/腹部环节等纯装饰节点可在设置里关（"精细模型"开关） |
| 面数 | 12.6k + N×5k ≈ 28k（6 只时） | 预算 8 万，安全 |
| 开关 | 设置页：`多智能体数量 1/3/6`、`青蛙`、`连接组驱动` | 全关 = M4 形态 |

## 7. 场景切换设计

### 7.1 需求与约束

切换要**快**。但现状是：`Scene.load()` 冷启动 10~20 秒（引擎初始化 + 149KB glb + 31MB 连接组）。
如果每次切换都重新 `Scene.load`，用户体验会崩。因此：

### 7.2 方案对比

| 方案 | 做法 | 切换耗时 | 代价 |
|---|---|---|---|
| **A. 单 glb 多区域（推荐）** | 一个 `world.glb` 里放多个"场景岛"，沿 X/Z 方向平移排布（例：草地岛在原点、河边岛在 x=+40、枯木岛在 x=-40）。切换 = 相机平滑飞过去 + 生物只在当前岛活动 | **瞬时（< 1s）** | 内存里始终持有多套场景几何；编辑器生成脚本变复杂 |
| B. 多 glb 按需加载 | 每个场景一个 glb，切换时 `Scene.load` 新文件 | 10~20s（不可接受） | 简单，但体验差 |
| C. 多 glb 预加载驻留 | 启动时把 3 个 glb 都载入，各自一个 `Component3D` | 首次 30~40s，之后瞬时 | 内存 x3，且多 Component3D 的渲染开销未验证 |

**决策：采用 A。** 理由：
- M4 已经证明"河 + 树 + 石"都在同一个 glb 里工作良好，扩展到多岛只是空间平移；
- 切换瞬间完成，可以做成**镜头拉远 → 飞越 → 落位**的转场，本身就是观感加分；
- 生物的"活动区域"是纯逻辑参数（`arenaCenter` + `arenaRadius`），与几何解耦。

### 7.3 场景预设（SceneProfile）

```ts
class SceneProfile {
  id: string;              // 'grass' | 'river' | 'rotten' | 'night'
  name: string;            // 显示名
  arenaCenterX: number;    // 活动区中心（对应 glb 里的某个场景岛）
  arenaCenterZ: number;
  arenaRadius: number;     // 活动半径
  riverEnabled: boolean;   // 是否有水域（决定临水/饮水逻辑）
  riverA0: number;         // 河流弧参数（若启用）
  riverA1: number;
  treeCount: number;       // 该场景的果树数量
  agents: AgentRoster;     // 放几只果蝇、是否有青蛙
  envPreset: EnvPreset;    // 昼夜时长、初始相位、光照
  cameraHint: CameraHint;  // 初始机位（yaw/pitch/radius/target）
  intro: string;           // 进场景时的一句话引导
}
```

**内置预设（首版 4 个）：**

| id | 名称 | 内容 | 玩法侧重 |
|---|---|---|---|
| `grass` | 草地（默认） | 现有 M4 场地，2 只果蝇，无青蛙 | 观察与投喂入门 |
| `river` | 河岸 | 河流占比更大，岸边有青蛙 | 救援玩法（吹风救果蝇） |
| `ecosystem` | 生态沙盒 | 3 只果蝇 + 青蛙 + 全部信息素机制 | 完整生态，本设计的核心场景 |
| `night` | 夜巡 | 固定夜晚，萤火虫（可选池），光照低 | 昼夜与趋光玩法的舞台 |

### 7.4 切换流程与状态处理

```
用户选场景 → 
  1) 保存当前场景状态快照（生物位置/HP/内驱力、信息素场、昼夜相位）到 SceneState
  2) 淡出 HUD（200ms）
  3) 相机飞越到目标岛（800ms，走抛物线，避免直视穿模）
  4) 切换 SceneProfile：重建 agents / 信息素场 / 环境控制器参数
  5) 恢复或初始化目标场景状态（支持"每个场景各自记住上次状态"）
  6) 淡入 HUD，显示 intro 一句话
```

**必须处理的边界：**
- 切换时 `BrainMount` 不重建（连接组继续跑，群状态延续）—— 这是"同一套脑"的又一次体现；
- 相机飞越期间**冻结行为层**（或大幅降速），避免穿模时青蛙扑空；
- 连接组仿真在切换期间**不暂停**（Worker 独立线程），否则重启有 20s 冷启动。

## 10. 验收标准（M5）

1. 3 只果蝇同场景运行，帧率不低于 M4 的 85%，连接组 tick ≤ 78ms；
2. §3.3 的 4 条群体行为现象中，**至少 3 条能被稳定复现**（并录像/截图存档）；
3. 青蛙在无人干预下能靠捕食果蝇自行维持饱食度 > 0 至少 10 分钟；
4. 反向验证：**关掉用户投喂后，果蝇先饿死、随后青蛙离场** —— 能量链条可被观察到断裂；
5. 场景切换 ≤ 1.5s（含转场动画），切换后生物状态正确、连接组未重启；
6. 「关于」页含科学边界说明（§0），措辞不得暗示"这是真实的多智能体生物仿真"；
7. 设置页可退化为 M4 形态（1 只果蝇、无青蛙、关信息素），且退化后功能不缺失。

## 11. 风险

| 风险 | 说明 | 对策 |
|---|---|---|
| **行为高度同步（最可能失败的点）** | 共用同一份连接组 + 相同接线 → 三只果蝇像影子 | 优先做 §2.4 的处境差异 + 参数扰动；仍同步则引入群偏移实验；**验收 2 是硬指标** |
| 连接组"接线错群" | 借用的群语义不对（尤其青蛙），行为无法解释 | 群号必须从 `neuron_meta.json` 程序读取，禁止手工硬编码；先在单只上验证再上多只 |
| 生态参数失衡 | 青蛙太强 → 果蝇被清空；太弱 → 没有威胁感 | 全部参数集中到 `EcoConfig`，设置页开放"生态强度"滑杆；验收 3/4 双向验证 |
| 单 glb 多岛导致体积膨胀 | 每岛一套几何 | 岛屿复用同一批网格（只平移节点），实测面数增量应 < 30% |
| 信息素场被玩家滥用 | 玩家反复在同一处投喂 → 场饱和失去区分度 | 场浓度上限钳制 + 衰减半衰期调参 |
| 科学表述被误读 | 见 §0 | 文案审查列为验收项 6 |

## 12. 开放问题（需要你拍板）

1. **多果蝇默认数量**：2 只（画面干净、性能富余）还是 3 只（群体行为更容易被观察）？
2. **"投喂青蛙"是否做成正式玩法**（把捕食者喂饱换和平），还是只作为隐含机制？
3. **场景切换的入口**：放在顶部栏独立按钮（显眼）还是设置页内（不打扰观察）？
4. **信息素场是否可视化**（一层半透明的暖色/红色雾），还是纯后台数值？
   可视化利于用户理解"为什么会聚集"，但会削弱"它自己在动"的神秘感。
